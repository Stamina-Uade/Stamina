01

TLS y proxy

Apache termina TLS y pasa sólo /v1/* a 127.0.0.1:8082. Si el backend cae, responde 502/503 en JSON.

02

Fastify + límite de tasa

Cuerpo ≤ 64 KB, quita __proto__. 60 pedidos/min por ruta + IP; 8/min en login, alta y recuperación.

03

Validación de esquema

Ajv con esquemas generados desde openapi.yaml. Si no cumple: bad_request o weak_password.

04

Guardia de auth

JWT HS256 fijado en código (iss trainer, aud trainer-app) y además la sesión viva en sesiones.

05

Idempotencia

Idempotency-Key + usuario + ruta + hash del cuerpo en la tabla idempotencia (24 h). Si se repite, la misma respuesta.

06

Ruta de dominio

rutas.ts traduce el contrato y llama a servicio.ts o al motor. El id de usuario sale sólo del token.

07

Repositorio

SQL siempre parametrizado; cada consulta filtra por usuario_id. Pool de 5 y tope de 10 s por consulta.

08

Respuesta o error

Éxito: { data }. Error: { error: { code, message } }, con códigos estables y Retry-After en el 429.

Cualquier etapa puede cortar → setErrorHandler (400 · 401 · 409 · 413 · 426 · 429 · 500 sin detalle en producción)Rutas públicas (/health, /version, /legal, /auth/*) saltean 04

Tres recorridos clave, paso a paso

Nombres reales del código: rutas, tablas y clases

aAlta, login y rotación del refresh

dominios/auth/servicio.ts · infra/cripto.ts
1
POST /auth/register
Genera un código de 6 caracteres y guarda su hash en Redis (15 min). Responde 202 igual, exista o no la cuenta: si existe, al dueño le llega sólo un aviso.
2
POST /auth/register/verify
Compara en tiempo constante; con 3 errores el código muere. Devuelve un registration_token: JWT de un uso, válido 10 min.
3
POST /auth/register/complete
Política de contraseña, aviso legal vigente y argon2id → usuarios + aceptaciones_legales + perfiles + primera sesión.
4
POST /auth/login
argon2id (si el correo no existe, con un hash de descarte para gastar el mismo tiempo) → access JWT de 30 min + refresh opaco de 30 días, guardado como hash en sesiones.
a los 30 min, o ante un 401
5
POST /auth/refresh
Bloquea la fila, la marca usada y crea la sucesora en la misma familia. Sucesor = HMAC(refresh viejo), así que el servidor puede volver a entregarlo sin haberlo guardado.
¿ese refresh ya se usó?
Reintento (≤ 2 min)La respuesta se perdió en el camino: se devuelve la misma sucesora con un access nuevo.
Reuso → familia revocadaPuede ser un robo: se revoca toda la familia y responde session_revoked.
Recuperación: /password/forgot → /verify → /reset sigue el mismo camino de código y permiso de un uso; al cambiar la clave se revocan todas las sesiones y se abre una nueva.

bGeneración del plan

dominios/plan/servicio.ts → motor/generador.ts (puro: no lee la base ni el reloj)
1
GET /plan → leer el perfil
Objetivo (o uno adicional de objetivos_usuario), nivel, deporte, zona horaria, días, fecha del evento, peso, edad y sexo. Si falta algo: profile_incomplete.
2
Hash estructural → ancla del bloque
SHA‑256 de objetivo, nivel, deporte, zona, fecha y días. Si cambió, el ancla vieja queda reemplazada y nace otra que empieza hoy. Si cambian el peso o el horario, el bloque sigue.
3
Macrociclo y fases
De 2 a 52 semanas: base → construcción → pico → afinamiento → carrera. El volumen arranca en el 55 % del pico, con una semana de descarga (72 %) cada 4.
4
Semanas → días → sesiones
Cada día elegido recibe un papel (fondo, calidad, suave, regenerativo, fuerza) → tipo, deporte (el triatlón rota), minutos, distancia, ritmos y zona de pulso.
5
Energía y avituallamiento
kcal por METs y peso; líquido, sodio, hidratos y geles por hora, y lo de antes y después. Usa siempre el clima por defecto: 22 °C y 55 % de humedad.
6
Juntar lo hecho → JSON
Cruza con actividades y series_gimnasio: done, totales por semana y racha. Textos según Accept-Language. Devuelve motor_version + input_hash.

4
Upsert con “el borrado gana”

5
PUT /v1/activities/{id}/route
Puntos ordenados por instante → recorridos_actividades.puntos (jsonb), sólo si la actividad es tuya y sigue viva.
